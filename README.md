| 11 | Monte Carlo π estimator | 2026-08-09 | `random.random()` (continuous sampling), `math.pi`, f-string format specifiers (`:>12.6f`, `:>10,`), named constants, averaging across repeated runs | Estimated π by counting random points inside a quarter circle — the value is measured, never computed. Learned that f-string format specs replace `round()` for anything displayed: `round()` returns a number that may still print badly, `f"{x:.6f}"` returns a string formatted exactly as asked. A table is just a header printed once plus fixed column widths, and **width is a minimum, not a maximum** — `'Absolute error'` is 14 chars so `:>12` silently widened the column and pushed every number 2 chars out of line. Skipped `math.sqrt` by comparing `x*x + y*y <= 1` instead. Biggest lesson was statistical: my first fix for noisy rows averaged the *estimates*, which stayed jumpy because errors above and below π cancel out — averaging tells you the estimator is unbiased, not that it's accurate. Taking `abs()` **inside** the loop and averaging the *errors* fixed it, since distances never cancel. The payoff: each error divided by the next gives ~3.1 against √10 ≈ 3.16, so error scales as 1/√N and one more decimal place costs 100× the samples. |
| 12 | Gambler's ruin | 2026-08-10 | `statistics` (`mean` / `median` / `stdev`), returning tuples and unpacking, returning a dict, chained comparison, booleans as numbers, separating compute from display | Simulated a biased random walk between an absorbing 0 and a target, then checked every simulated ruin rate against the closed-form formula — the simulation only becomes evidence once it reproduces the known answer. Learned to make a function `return` instead of `print`: my `run_trial` printed its own report, which meant it could only ever be used one way, and the table was impossible until the numbers came back as values. Six of them was too many to unpack positionally, so it returns a dict — `stats["median"]` survives a reordering that `a, b, c, d, e, f = ...` does not. `statistics.mean` on a list of booleans gives the proportion for free, since `True` is 1. Two crashes worth remembering: `(1 - p) / p` divides by zero at `p = 0`, and comparing `p == 0.5` is only safe because 0.5 is exactly representable in binary — most decimals are not. Also that clamping bad input to a legal value is worse than rejecting it: it hands back a confident wrong answer, and without a `0 < start < target` check every game ends in 0 rounds and reports 100% success. The statistics were the real lesson — stdev 82.5 against mean 101.5, and median 78 well below the mean, so duration is wildly spread and right-skewed. Mean rounds peaks exactly at the fair game and matches `start × (target − start)` = 100; any edge either way ends things sooner. And a 1% shift in p moves ruin from 50% to 60%, which is the whole business model of a casino. |
| 13 | Bank account simulator | 2026-08-11 | first OOP: `class`, `__init__`, `self`, methods; raising my own exceptions (`raise ValueError`); the `__str__` dunder | First class, and the whole shape of the language changed: instead of functions taking data as arguments and handing back new data, the data and the rules that guard it live together in one object, and methods mutate `self`. The `self` click was the lesson — `acc1.deposit(1000)` silently passes `acc1` in as `self`, so the method always knows which account to change without me telling it, which is exactly why `acc1` and `acc2` never interfere. Learned that state set in `__init__` is per-instance: because `self.balance` and `self.history = []` are assigned there, every account gets its own balance and its own list — the `history` trap from the to-do list (a list is shared if you're not careful) doesn't bite here precisely because `__init__` runs fresh for each object. Raising my own `ValueError` instead of catching someone else's was new, and it's the honest version of the gambler's-ruin lesson: refuse a bad withdrawal rather than clamp it and hand back a confident wrong balance. Order matters in the guards — check the amount is positive *before* checking funds, since a negative amount is malformed regardless of balance. `__str__` was my first dunder beyond `__init__`: define it and `print(acc)` shows `Owner: Jaume, Balance: $6000` instead of a `<BankAccount object at 0x...>`. And a callback to the Zetamac trainer — `time.time()` in the log printed a raw `1754899200.45`, so I swapped it for `datetime.now().strftime("%Y-%m-%d %H:%M")` to get a timestamp a human can read. |
| 14 | Dice & Monte Carlo in NumPy | 2026-08-15 | `numpy`, `default_rng`, vectorization, boolean masks, `np.bincount`, `time.perf_counter()` benchmarking, functions as arguments and `*args` | Rewrote projects 10 and 11 so no Python loop touches a single trial — generate all N values as one array, let compiled code do the arithmetic. The mental shift is that a comparison on an array returns an *array of booleans*, and since `True` is 1, `mask.mean()` is the proportion directly: π is `4 * ((x**2 + y**2) <= 1).mean()`, no counting. `np.bincount` replaced `Counter` the same way — one C pass, using each value as its own index. Two bugs, both silent. `rng.integers(1, 7)` is exclusive on the high end unlike `random.randint(1, 6)`, and I wrote `(0, 7)` — which doesn't crash, it just builds a seven-sided die whose faces all land near 14.3% instead of 16.67%. Only comparing against the theoretical column caught it, so the output table was the test. The other was `return 1 - tails` instead of `n - tails`: confident nonsense, no traceback. Learned that `.mean()` is a *method on an ndarray*, so a plain list doesn't have one — `np.mean(list)` works because the function converts, the method can't. Then repeated my project 11 mistake exactly: measured error as `abs(mean(estimates) - π)`, which lets overshoots cancel undershoots and claimed 0.000009 error at a million samples. `mean(abs(estimates - π))` restored the clean 3.2× per 10×. Knowing a lesson and applying it are apparently different skills. Also had to make the simulators `return` instead of `print` before they could be benchmarked at all, since console I/O would land inside the timed section — the same separate-compute-from-display lesson as project 12, now with a concrete cost. `benchmark.py` was my first time passing functions as arguments (`time_call(fn, *args)`, no parens on `fn`) and using `*args` to absorb the two signatures having different arity, and taking `min()` of 3 runs rather than the mean, since noise only ever makes a run slower. The result that surprised me: dice sped up ~50× but π only ~6×, same technique. π allocates six arrays per call — x, y, x², y², their sum, the mask — about half a gigabyte at 10 million trials, so it's bound by memory bandwidth while the dice are bound by the CPU. Vectorization buys speed by spending memory, and once you're memory-bound it stops paying. π's speedup also *falls* as N grows (14× at 10k, 5.6× at 1M) because small arrays still fit in cache and hide the cost — the flattering number is the dishonest one. |

My tracker is a spreadsheet: three `Round N` columns side by side, decimal commas, and pre-filled empty future dates. `melt` collapses those three columns into one row per attempt, and my first version called it and threw the result away — Pandas methods return new frames instead of mutating, which is the `.strip()` / `sorted()` lesson from project 6 for the third time. Order mattered twice: `astype(int)` only works after `dropna`, since `NaN` forces a float column, and the header check in a CSV writer has to happen before opening in append mode because opening creates the file. Learned a Series isn't a string — Python's string methods need the `.str` bridge to apply down a column — and that `groupby` moves its key into the index, hence `reset_index()`. The real conceptual jump was realising I had two datasets, not one: 90 per-attempt rows and 30 daily rows. A 7-day rolling average over the per-attempt frame spans 2⅓ days and mixes round 1 with round 3, so it belongs on the daily frame. `.transform` was the tool I didn't know I needed — it computes a group value and broadcasts it back to every original row, which let me subtract each day's average from each attempt and measure the round effect without the month-long upward trend contaminating it. `np.polyfit` needs a numeric x-axis, so dates became `(date - date.min()).dt.days`. Best lesson was statistical, again: I found a 5.6-point weekday gap and a 1.4-point fatigue effect, then worked out the standard errors — 4–5 observations per weekday against a daily spread of 7.5 means the weekday result is pure noise, and the round effect is only ~1.5 standard errors even after detrending. Two findings, both dissolved on inspection. The +0.73 points/day trend line is real but already over-predicting: the rolling average flattens against it in the last week, so it describes the past and shouldn't be extrapolated.
